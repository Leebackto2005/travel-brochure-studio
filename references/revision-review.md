# 多轮修改：基线、改动要求与交付核对

用于已经出过稿、连续收到补图/改字/换封面，或需同时交付PDF和源文件的项目。单句小改直接沿用当前版本，不重复完整访谈；此流程不要求用户填写技术表单。

## 把聊天决定落到具体文件和位置

先查看已交付目录、最近的修改记录和对话，区分“正在编辑的源文件”“已交付PDF”“试导出的候选”。文件修改时间或名称带“最终”不足以认定它是制作基线。记录所用路径和SHA256，已有项目记录就原地续写。

新项目的工作区、素材及分版本交付目录按 [项目目录规范](project-folders.md) 管理；旧项目保留现有路径，记录对应关系即可。

对容易返工的多轮项目，制作约定至少保留以下信息；内容明确时由Agent整理，不重新向用户提问：

| 记录 | 实际用途 |
|---|---|
| 当前PDF、可编辑源文件、构建数据及其对应版本 | 防止拿旧HTML覆盖新PDF，或只更新打包文件中的一份 |
| 本次允许改动的内容与页码；保留项 | 将“加酒店”限定为展示页，避免自动改变每日住宿承诺 |
| 已确认事实、确认来源与适用范围 | 用户确认一餐包含，只更新该餐；换封面不自动确认其他新业务口径 |
| 暂缓事项及处理方式 | “先不管”表示暂缓相关事项，不表示同意猜一个答案，也不取消已回答的部分 |
| 需要在成品中出现、消失、保留或移动的内容 | 修改前就知道怎样检查改对了，避免只检查文件能打开 |

新确认按字段和范围覆盖旧信息。行程、KV、参考版式出现冲突时，明确冲突落在哪一项；参考图中的日期、套餐、酒店和价格不能整批覆盖产品事实。

建立简短页码映射：“物理第几页 → 页面用途 → 第几天/酒店组/条款”。例如第8天不一定在PDF第8页。旧HTML没有`data-page-id`或`data-day`时先inspect，找到可唯一定位的标题和容器；不把缺少属性理解为没有行程，也不为了适配工具重建整册。

## 修改前写下可核对的结果

把本轮要求转换成少量明确检查，依照实际请求选择：

- 酒店：名称出现在指定页、组数符合要求、外观与客房图框成对；具体图像身份仍需看图核实。
- 航班：在对应当天容器内，PDF中出现在该日标题之后；旧时刻说明已删除，送机与早餐等保留文字仍在。
- 餐食：已确认的包含/自理口径保留；图片图注没有升级为固定菜单。
- 封面：图片对应已确认原件，满版方式及尺寸明确；纯图片上的价格与日期通过放大/OCR辅助后逐字核对，不能靠PDF原生文字检查。
- 范围：页数和页序符合约定；未改页与基线一致。需要新增续页时更新映射，不能继续使用旧页号合并。

检查只覆盖本次请求和受影响的既有确认，不将这次某个产品的17页、酒店数量或航班时刻固定成以后默认值。

## 同步源文件，核对实际交付的一对文件

有JSON构建源的项目优先修改JSON后生成HTML；既有手工HTML按页补丁。只改PDF封面时仍按交付约定同步需要保留的源文件，包括图片和页面尺寸。不要修改源文件后继续打包上一次PDF，也不要把“已导出”视为“所有交付文件一致”。

沿用 [HTML/PDF流程](html-pdf.md) 的渲染和指定页合并。然后进行两种互补核对：

1. `pdf_pages.py verify`证明未改页在指定渲染器/DPI下与基线一致；允许变化的页不会因此自动被判定改对。
2. `check_delivery.py`按明确要求检查最终PDF与交付HTML中的页码、文字、顺序和节点数量；只检查列出的要求，不声称整份源文件与PDF完全等价。

示例规格如下，值和选择器均需先按本项目实际文件填写；`page`是从1开始的物理页码：

```json
{
  "schema_version": 1,
  "page_count": 4,
  "html_checks": [
    {"id":"hotel-rows", "page":3, "selector":".hotel-row", "count":1},
    {"id":"return", "page":4, "selector":".day[data-day='2']", "count":1,
     "ordered":["返程日", "已确认返程信息"], "excludes":["旧返程信息"]}
  ],
  "pdf_checks": [
    {"id":"return", "page":4, "ordered":["返程日", "已确认返程信息"],
     "contains":["需要保留的送机说明"], "excludes":["旧返程信息"]}
  ]
}
```

```powershell
python scripts/check_delivery.py --html final.html --pdf final.pdf --spec requirements.json --report requirements-report.json
```

`contains`检查出现，`excludes`检查已移除，`ordered`检查片段先后。HTML选择器只在该页内查找；省略选择器时检查整页。`count`默认1，设为0可检查旧节点已移除；匹配多个节点时文字要求逐节点检查。PDF使用页面原生文本，跨行空白和全角形式归一化，数字及标点仍参与比较。图片页无原生文字时明确不通过文字检查，转为视觉/OCR核对，不伪称通过。

工具返回0表示所列要求通过，1表示要求不符，2表示参数/文件有误。报告记录输入与规格哈希；不覆盖输入，已有报告另存或显式`--overwrite`。HTML的隐藏文字及PDF旧文本层可能被提取，工具不证明可见性、事实准确、图片对应、字体、授权或视觉验收。只有PDF或PPTX的项目不要为了使用本工具而转换为HTML；可仅写`pdf_checks`。

## 报警与交付

渲染报告中的`overflow_count`对应越过页面/纸面、页脚边界或裁切等阻断问题。`spacing_warning_count`只表示内容进入纸面底部padding、但仍在纸面和页脚边界内，需查看对应PDF页的实际间距；不能把它当成裁切，也不能靠加`--allow-incomplete`绕过硬错误。

`flight_days`列出标准`.flight-strip`和旧版`.flight-callout`，优先读取`data-day`，否则从已知日标题形式提取并注明`heading-label`。`day:null`或`placement:unassigned`须人工定位；非这两种结构不在识别范围内。航班清单用于定位，不证明日归属已确认。

交付前检查最终打包的文件，给出唯一明确的当前版本入口。保留前一版；说明哪些页改了、哪些要求已核对、哪些图片/业务事项仍待确认。需要用户确认时，提供实际候选或样张以及该次决定的影响，沿用已获得的授权，不另加一次“是否可以开始”。
